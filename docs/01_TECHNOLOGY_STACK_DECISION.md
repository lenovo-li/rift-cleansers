## 执行摘要

**最终推荐：Godot 4.7.2 稳定版 + GDScript + 主机权威ENet/Steam架构**

从零开始创建项目，采用成熟游戏引擎而非Web技术栈。主要理由：

1. 单人开发时间预算有限，引擎编辑器节省大量底层工作
2. 1000-2000敌人需要MultiMesh、对象池和空间分区，Godot原生支持
3. Steam集成、手柄、音频混合、粒子系统已内置
4. 主机权威网络架构已有成熟参考实现
5. 低多边形3D渲染管线完整

## 1. 决策背景

### 1.1 项目约束（来自设计文档）

| 约束 | 技术影响 |
|---|---|
| 单人开发 | 工具链必须简单，不能维护复杂构建 |
| 1-4人联机 | 需要主机权威架构和状态同步 |
| 1000-2000敌人 | 需要实例化渲染、对象池、空间分区 |
| 20-25分钟单局 | 需要稳定性能，无内存泄漏 |
| 技能四段进化 | 需要粒子系统和Shader |
| 掉线重连 | 需要快照序列化和状态恢复 |
| Steam发布 | 需要Steamworks集成 |
| 手柄支持 | 需要输入映射和振动 |
| 低多边形3D | 需要3D渲染管线和模型导入 |

### 1.2 开发者背景

- 主要擅长编程，不擅长美术
- 有编程经验，需要快速迭代游戏逻辑
- 需要可视化编辑器辅助场景和UI布局
- 希望尽量使用免费开源工具

## 2. 候选方案对比

### 2.1 方案A：Godot 4.x

#### 技术栈

- **引擎**：Godot 4.7.2 稳定版（MIT许可证）
- **主语言**：GDScript，强制类型标注
- **性能扩展**：C++/GDExtension（仅在Profiler确认热点后使用）
- **联机**：Godot高层多人API + ENet（开发期）+ GodotSteam（Steam版）
- **渲染**：Godot 4.x Forward+ / Mobile 渲染器
- **粒子**：GPUParticles3D + CPUParticles3D
- **UI**：Control节点 + Themes
- **音频**：AudioStreamPlayer + AudioBus混音
- **输入**：Input映射 + 手柄振动
- **构建**：Windows导出模板
- **版本控制**：Git + Git LFS

#### 优势

✓ **编辑器完整**：场景、UI、粒子、动画、Shader可视化编辑  
✓ **3D管线成熟**：glTF导入、MultiMesh、LOD、骨骼动画  
✓ **网络API高层**：MultiplayerPeer抽象，ENet/WebRTC/Steam可切换  
✓ **免费开源**：MIT许可证，无运行时分成，源码可审计  
✓ **对象池和空间分区**：可自行实现或使用社区插件  
✓ **GodotSteam成熟**：社区维护的Steamworks绑定  
✓ **手柄原生支持**：InputEventJoypadButton/Motion，振动API  
✓ **单人开发友好**：编辑器UI降低美术门槛  
✓ **文档完善**：中文文档、教程、社区活跃  
✓ **快速迭代**：GDScript热重载，无需编译  

#### 劣势

✗ **GDScript性能**：弱于C++，但1000敌人关键在架构而非语言  
✗ **引擎Bug**：4.x仍在快速迭代，需固定版本号  
✗ **插件生态小于Unity**：但核心功能已内置  
✗ **移动端性能**：本项目不考虑移动端，不影响  

#### 实现路径

1. **M0（2周）**：Godot 4.7.2项目 + 玩家移动 + 1000方块压测
2. **M1（4-6周）**：10分钟单人灰盒，GDScript实现核心战斗
3. **M2（3-4周）**：ENet局域网2人原型
4. **M3（8-12周）**：垂直切片美术，Blender→glTF工作流
5. **M4（6-8周）**：GodotSteam + Steam Relay，1-4人完整联机

#### 技术风险

| 风险 | 概率 | 应对 |
|---|---|---|
| GDScript性能不足 | 中 | Profiler定位热点，C++重写 |
| Godot 4.x Bug | 中 | 固定版本，社区活跃修复快 |
| GodotSteam版本不匹配 | 低 | 使用稳定版本组合，提前测试 |
| MultiMesh上限 | 低 | 分批渲染，远处LOD降级 |

### 2.2 方案B：Web技术栈（TypeScript + Canvas/WebGL）

#### 技术栈

- **语言**：TypeScript
- **渲染**：Canvas 2D 或 PixiJS（WebGL 2D）
- **联机**：WebSocket（服务器权威）或 WebRTC DataChannel（P2P）
- **信令**：Node.js信令服务器
- **中继**：TURN服务器（复杂网络环境）
- **桌面封装**：Electron
- **Steam集成**：Greenworks或自定义原生模块
- **构建**：Webpack/Vite + Electron Builder

#### 优势

✓ **JavaScript生态**：NPM包丰富  
✓ **跨平台天然**：浏览器、桌面、理论上移动端  
✓ **热重载快**：开发期刷新浏览器即可  

#### 劣势

✗ **引擎缺失**：场景编辑器、粒子系统、UI布局需自建或引入框架  
✗ **3D支持弱**：Canvas 2D不支持3D，Three.js/Babylon.js增加复杂度  
✗ **性能上限低**：1000-2000敌人在浏览器JS引擎中难以优化  
✗ **Steam集成复杂**：Greenworks维护状态不明，自定义桥接成本高  
✗ **手柄支持弱**：Web Gamepad API功能有限，振动支持差  
✗ **音频混合弱**：Web Audio API不如专业游戏引擎  
✗ **网络自建**：WebSocket服务器需部署维护，WebRTC信令+TURN复杂  
✗ **对象池和空间分区**：需自行实现  
✗ **Electron体积大**：打包100-200MB基础体积  
✗ **单人开发成本高**：大量底层工作需手动实现  

#### 技术风险

| 风险 | 概率 | 应对 |
|---|---|---|
| 1000敌人性能瓶颈 | 高 | WebGL优化，但上限仍低于原生 |
| Steam集成失败 | 中 | 找到可用桥接或放弃Steam独占功能 |
| 服务器运维成本 | 中 | WebSocket需持续运行，P2P需TURN |
| Electron打包问题 | 中 | 原生模块编译、签名复杂 |

### 2.3 方案C：其他成熟引擎（Unity/Unreal/Stride）

#### Unity

- **优势**：生态最大，Asset Store丰富，C#性能好
- **劣势**：运行时分成（收入超阈值），许可证复杂，编辑器重量级
- **判断**：对单人开发者，Godot免费且足够，Unity优势不明显

#### Unreal Engine

- **优势**：AAA级渲染，蓝图可视化编程
- **劣势**：引擎体积巨大，编辑器学习曲线陡峭，低多边形3D用不上高级渲染
- **判断**：过度工程，不适合本项目

#### Stride（前Xenko）

- **优势**：MIT许可证，C#，轻量级
- **劣势**：社区小，文档少，GodotSteam无对应方案
- **判断**：未经大规模验证，风险高于Godot

#### Bevy（Rust ECS）

- **优势**：性能极高，ECS架构现代
- **劣势**：无可视化编辑器，Rust学习曲线陡峭，生态不成熟
- **判断**：适合引擎开发者，不适合单人游戏开发者

## 4. 最终推荐

### 4.1 决策结论

```yaml
引擎: Godot 4.7.2 稳定版
主语言: GDScript（强制类型标注）
性能扩展: C++/GDExtension（Profiler确认热点后）
联机模型: 主机权威 Listen Server
开发期传输: ENet（Godot MultiplayerPeer）
Steam传输: GodotSteam MultiplayerPeer + Steam Relay
首发平台: Windows 10/11，Steam
渲染方向: 低多边形3D，Forward+渲染器
正式项目: 从零创建，不复用现有node_modules
node_modules: 归档到archive/或删除
```

### 4.2 推荐理由

1. **开发效率最高**：编辑器、粒子、UI、音频、输入已内置
2. **性能足够**：MultiMesh可支持1000-2000敌人（关键在架构）
3. **联机成熟**：高层多人API + GodotSteam有完整教程
4. **成本最低**：MIT许可证，无运行时分成
5. **风险可控**：社区活跃，文档完善，有成功案例

### 4.3 为什么不选择Web技术栈

| 问题 | Web方案成本 | Godot方案成本 |
|---|---|---|
| 场景编辑器 | 需自建或引入框架 | 内置 |
| 粒子系统 | 需自建 | 内置GPU/CPU粒子 |
| UI布局 | HTML/CSS或Canvas手动布局 | 内置Control节点 |
| 3D渲染 | Three.js集成+学习 | 内置3D管线 |
| 1000敌人优化 | JS引擎上限+手动优化 | MultiMesh+GDScript/C++ |
| Steam集成 | Greenworks或自定义桥接 | GodotSteam插件 |
| 手柄振动 | Web API受限 | 原生支持 |
| 音频混合 | Web Audio API | 内置AudioBus |
| 服务器部署 | WebSocket需运维 | 无需独立服务器 |
| **总开发时间** | **+3-6个月底层工作** | **立即开始游戏逻辑** |

## 5. 三大技术风险

### 5.1 风险1：GDScript性能瓶颈

**场景**：1000-2000敌人逻辑更新导致主线程超过16ms

**概率**：中（30%）

**应对**：
1. 架构优先：对象池、空间网格、分层更新频率
2. Profiler定位：GDScript性能分析器找热点函数
3. C++重写：GDExtension重写热点（敌人更新、碰撞查询）
4. 预算控制：近处10Hz，远处2Hz，超出预算停止生成

**早期信号**：M1灰盒500敌人时主线程>10ms

**最晚验证时间**：M1结束前

---

### 5.2 风险2：四人终局GPU瓶颈

**场景**：4人20分钟后粒子、特效、尸体导致GPU帧时间>16ms

**概率**：中（40%）

**应对**：
1. MultiMesh普通敌人
2. 队友粒子透明度50%-80%
3. 尸体5秒后淡出删除
4. 质量档：低配关闭队友拖尾、降低粒子数
5. 伤害数字聚合
6. 屏幕外剔除

**早期信号**：M2联机原型2人时GPU>10ms

**最晚验证时间**：M4四人测试

---

### 5.3 风险3：联机状态分叉

**场景**：客户端Boss血量、玩家位置、掉落与主机不一致

**概率**：高（60%，架构不当时）

**应对**：
1. 主机权威：所有逻辑结果由主机决定
2. 固定种子：随机数可复现
3. 快照同步：关键状态定期全量同步
4. 客户端预测：仅本地移动预测，主机校正
5. 不同步：粒子、尸体、伤害数字客户端本地

**早期信号**：M2原型Boss血量不一致

**最晚验证时间**：M2结束前

## 6. 技术选错的返工成本

### 6.1 如果选Godot但失败

**失败场景**：
- GDScript性能不足，C++重写成本过高
- Godot 4.x重大Bug无法修复
- GodotSteam无法满足需求

**返工成本**：
- 迁移到Unity/Unreal：核心逻辑可复用（设计和算法），场景和资源重做
- 预计返工：**1-2个月**（场景、粒子、UI重建）
- 可复用：游戏逻辑、数值、美术资产（模型、音效）

### 6.2 如果选Web技术栈但失败

**失败场景**：
- 1000敌人性能无法达标
- Steam集成失败
- 联机服务器运维成本过高

**返工成本**：
- 迁移到Godot/Unity：底层系统全部重写
- 预计返工：**3-6个月**（引擎迁移+场景重建+网络重构）
- 可复用：游戏设计文档、美术资产（需转换格式）
