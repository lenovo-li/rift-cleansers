## 执行摘要

本文档记录项目开发过程中的技术风险及其实际结果，包括：
- 风险描述和概率/影响评估

- 最终验证结果

**风险等级**：
- 🔴 **高风险**：概率高或影响严重，可能导致项目失败
- 🟡 **中风险**：概率中等或影响中等，可能导致返工
- 🟢 **低风险**：概率低且影响小，可接受

**实际结果**：
- ✅ **已解决**：风险未发生或成功应对
- ⚠️ **部分解决**：风险发生但影响可控
- ❌ **未解决**：风险发生且影响显著

## 高风险项回顾 🔴

### R01：大量敌人性能瓶颈 ✅

**描述**：目标在中端 PC 上渲染 1000-2000 个敌人并保持 60 FPS。

**预测**：
- 概率：中（40%）
- 影响：高（核心卖点）

**实际结果**：✅ **未发生，性能超预期**

**验证数据**：
- 500 敌人单机：平均 396 FPS，1% low 105
- 500 敌人联机：主机 202 FPS，客户端 240 FPS
- 1000 敌人压测：未进行（500 敌人已足够）

**成功原因**：
1. ✅ M1 阶段完成 500 敌人压测，性能充足
2. ✅ 对象池 + 空间网格从第一天使用
3. ✅ MultiMesh 实例化渲染
4. ✅ 分层更新（近处高频，远处低频）
5. ✅ 每周性能监控，无回归

**经验教训**：
- Godot 4.7.2 + GDScript 性能对此类游戏完全足够
- 无需 C++/GDExtension 优化
- 架构设计比语言性能更重要

---

### R02：四人终局 GPU 瓶颈 ✅

**描述**：4 人 20 分钟后大量粒子、技能特效、尸体导致 GPU 帧时间超 16ms。

**预测**：
- 概率：高（50%）
- 影响：高（多人体验核心）

**实际结果**：✅ **未发生，性能达标**

**验证数据**：
- 500 敌人联机：主机 202 FPS，客户端 240 FPS
- 4 人联机：未做 1000 敌人压测，但 500 敌人性能充足

**成功原因**：
1. ✅ MultiMesh 渲染普通敌人
2. ✅ 尸体 5 秒淡出删除
3. ✅ 粒子系统数量控制
4. ✅ 画质档位（低/中/高）
5. ✅ 溶解死亡 Shader 优化

**未实现的预防措施**：
- ❌ 队友粒子透明度调节（未实现，但不影响性能）
- ❌ 4 人 1000 敌人压测（500 敌人已达标，未做极限测试）

**经验教训**：
- 适度的特效控制即可，无需极端优化
- 画质档位是性能兜底的有效手段

---

### R03：联机状态分叉 ✅

**描述**：客户端 Boss 血量、玩家位置、掉落与主机不一致。

**预测**：
- 概率：高（60%，如果架构不当）
- 影响：极高（联机无法玩）

**实际结果**：✅ **未发生，架构设计成功**

**验证数据**：
- M2 联机原型：10 分钟无状态分叉
- 掉线重连：状态恢复正常
- 500 敌人联机：Boss 血量阶段一致

**成功原因**：
1. ✅ 主机权威：所有逻辑由主机决定
2. ✅ 固定种子生成：地图和敌人用固定种子，主机客户端一致
3. ✅ 参数同步而非实体同步：只同步敌群参数，不同步每个敌人位置
4. ✅ 客户端只预测移动：玩家移动客户端预测，主机校正
5. ✅ 早期验证：M2 阶段就验证联机，避免后期重构

**经验教训**：
- 主机权威架构对此类游戏是最佳选择
- 固定种子生成大幅简化同步复杂度
- 早期验证联机架构至关重要

---

### R04：P2P 连接可靠性 ⚠️

**描述**：P2P WebRTC 连接在复杂网络环境下可能失败。

**预测**：
- 概率：中（30%）
- 影响：高（联机体验）

**实际结果**：⚠️ **部分解决，已知限制**

**验证数据**：
- ⚠️ 跨 NAT 连接尚未实测（本机回环可拿到 STUN 公网候选）
- ✅ 可选 TURN 中转配置（ice_servers.json）
- ❌ 双方都在对称 NAT 后面且无 TURN 时连接失败

**已实现的措施**：
1. ✅ WebRTC + 公共 STUN
2. ✅ 可选 TURN 中转配置
3. ✅ ENet 局域网作为备选
4. ✅ 邀请码 + 回应码简化连接

**已知限制**：
- ❌ 对称 NAT 无 TURN 时无法连接（建议用 Tailscale + 局域网模式）
- ❌ P2P 插件只打包 Windows x64（其他平台需补库）

**经验教训**：
- P2P WebRTC 能覆盖大部分场景，但不是 100% 可靠
- ENet 局域网备选方案是必要的
- 文档应明确说明限制和备选方案

## 中风险项回顾 🟡

### R05：技能数量不足 ✅

**描述**：单个角色只有 6 个技能，可能不够多样。

**预测**：
- 概率：中（30%）
- 影响：中（可玩性）

**实际结果**：✅ **未发生，内容充足**

**实际内容**：
- 24 个技能（4 角色 × 6 技能）
- 每个技能四段进化（Lv1/3/5/8）
- 32 件装备改变规则
- 9 种精英词缀
- 4 张地图 × 3 首音乐

**成功原因**：
1. ✅ 技能四段进化提供深度
2. ✅ 装备改变规则而非微调数值
3. ✅ 精英词缀增加变化
4. ✅ 天赋树提供局外成长

**经验教训**：
- 深度（技能进化）比数量更重要
- 装备 + 词缀 + 天赋提供足够变化

---

### R06：Boss 战不有趣 ✅

**描述**：Boss 可能变成数值检验，缺乏机制乐趣。

**预测**：
- 概率：中（40%）
- 影响：中（高潮体验）

**实际结果**：✅ **未发生，Boss 战有趣**

**实际设计**：
- 4 个 Boss，各有特色技能组合
- 三阶段（60% / 30% 切换）
- 随机词缀（狂暴、坚韧、召唤、爆裂）
- Boss 预警机制（红色箭头、范围圈）

**成功原因**：
1. ✅ 每个 Boss 有特色技能（冲锋、冰雨、钻地、根须）
2. ✅ 三阶段提供节奏变化
3. ✅ 随机词缀增加重玩性
4. ✅ 预警机制让玩家有应对空间

**经验教训**：
- 预警机制是关键（可读、可躲）
- 阶段切换提供节奏变化
- 随机词缀增加重玩性

---

### R07：美术风格不统一 ✅

**描述**：使用多个素材包可能导致风格不统一。

**预测**：
- 概率：中（30%）
- 影响：中（视觉体验）

**实际结果**：✅ **未发生，风格统一**

**实际方案**：
- Blender 程序化生成平滑中模（全部 29 个模型）
- 统一顶点色风格
- Kenney 素材仅用于早期原型（已替换）
- Fusion Pixel 字体统一 UI

**成功原因**：
1. ✅ 程序化生成保证风格一致
2. ✅ 所有模型附 .blend 源文件
3. ✅ 顶点动画系统统一
4. ✅ 音效音乐都是原创或程序化生成

**经验教训**：
- 程序化生成是单人开发的最佳选择
- 统一的工具链和流程保证风格一致

---

### R08：内容产能不足 ✅

**描述**：单人开发可能无法完成足够的内容。

**预测**：
- 概率：高（50%）
- 影响：中（游戏时长）

**实际结果**：✅ **未发生，内容充足**

**实际产能**：

- 4 张地图（4 个 Boss）
- 9 种精英词缀

2. ✅ 程序化生成（模型、音效、音乐）
3. ✅ 工具链完善（build_models.py, compose_music.py）
4. ✅ 复用机制（精英词缀、Boss 词缀）

**经验教训**：
- 数据驱动 + 程序化生成是产能关键
- 工具链投资回报率高
- 复用机制减少重复工作

## 低风险项回顾 🟢

### R09：Godot 版本升级破坏兼容性 ✅

**描述**：Godot 版本升级可能导致 API 变化。

**预测**：
- 概率：低（20%）
- 影响：中（返工）

**实际结果**：✅ **未发生，版本稳定**

**实际情况**：
- 使用 Godot 4.7.2，全程未升级
- 无 API 破坏性变化

**经验教训**：
- 锁定小版本（4.7.x）是正确选择
- Godot 4.7 稳定性良好

---

### R10：Git LFS 配额超限 ✅

**描述**：模型和音频文件可能超过 Git LFS 配额。

**预测**：
- 概率：低（10%）
- 影响：低（迁移成本）

**实际结果**：✅ **未发生，配额充足**

**实际情况**：
- 模型使用程序化生成，源文件较小
- 音乐使用 MIDI + FluidSynth，ogg 文件较小
- 音效程序化生成，无大量素材

**经验教训**：
- 程序化生成减少仓库体积
- Git LFS 对此类项目足够

5. **文档应明确限制**：已知限制写清楚，用户有预期不会失望
